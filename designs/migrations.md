# Alembic Migrations

Dev runs **SQLite**, production runs **MySQL**. Every migration must work on both, and the
test suite only ever exercises the SQLite path — so a MySQL-only failure is invisible until
deploy. That asymmetry is the reason for most of the rules below.

## The core rule: `batch_alter_table` for every ALTER

Always use `batch_alter_table` for ALTER operations (add/drop columns, add/drop constraints):

```python
with op.batch_alter_table("flights") as batch_op:
    batch_op.add_column(sa.Column("aircraft_id", sa.Integer(), nullable=True))
```

SQLite does not support `ALTER` natively — batch mode implements it as create-new-table,
copy rows, drop old, rename. MySQL executes it as an ordinary `ALTER`.

`env.py` sets `render_as_batch=True` as a safety net for autogenerated migrations, but prefer
writing `batch_alter_table` explicitly in migration code: the safety net only covers what
autogenerate produced, not hand-written operations.

**Exception:** `op.create_table` and `op.drop_table` work on both dialects without batch mode.

## Named constraints

Name constraints explicitly so `downgrade()` can reference them:

```python
batch_op.create_foreign_key("fk_flights_aircraft_id", "aircraft", ["aircraft_id"], ["id"])
```

Unnamed constraints get dialect-generated names that differ between SQLite and MySQL, which
makes a portable downgrade impossible to write.

## Column renames on MySQL need `existing_type`

MySQL's `CHANGE COLUMN` restates the full column definition, so a rename without
`existing_type` loses the type:

```python
batch_op.alter_column("old_name", new_column_name="new_name",
                      existing_type=sa.String(length=64))
```

## Canonical patterns to copy

- **`004_flight_profiles.py`** — the reference for "create a table *and* add an FK column to
  an existing table" in one migration. Start here when adding a related entity.
- **Migrations 014 and 015** — the reference for dialect-specific branching, via
  `op.get_bind().dialect.name == "mysql"`. Use this only when a rule genuinely cannot be
  expressed portably; it doubles the paths that need testing.

## Datetime columns

Choosing the column *type* for a datetime is a separate decision with its own trap
(MySQL truncating to whole seconds while SQLite keeps microseconds — the cause of the
migration-015 bug). That decision, the `TZDateTime` type, and when `fsp=6` is required
are documented in **`time-alignment-audit.md`** — read it before adding a datetime column.

## Checklist before merging a migration

1. Every ALTER wrapped in `batch_alter_table`.
2. Every constraint named.
3. Any rename carries `existing_type`.
4. `downgrade()` written and it references constraints by name.
5. Datetime columns follow `time-alignment-audit.md`.
6. Run `alembic upgrade head` then `alembic downgrade -1` locally — SQLite catches the
   batch-mode mistakes, which are the most common failure.
