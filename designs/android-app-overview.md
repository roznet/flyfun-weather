## Implementation Status

All four core phases are built and verified against both offline fixtures (`FLYFUN_MOCK=1`) and the live local HTTPS backend (`https://localhost.ro-z.me:8443`), with two explicit follow-ups noted below:

- **Phase 0 (Server & CI)**: `device_tokens.platform` (`"ios"` | `"android"`, migration `110`), `FcmPushSender` in `src/weatherbrief/notify/push.py`, `/.well-known/assetlinks.json` in `deploy/weather.flyfun.aero.caddy`, and `.github/workflows/android.yml` + `android-ui-nightly.yml` (runs JVM unit tests across all 4 modules, Android lint, and debug APK compilation).
- **Phase 1 (Core App & App-Local Pure-JVM Libraries)**: `:flyfun-common`, `:rzflight`, Auth (`AndroidTokenStore` backed by Android Keystore AES-GCM), Adaptive Flight List & Trips, Add/Edit Flight, Aircraft CRUD, Advisory & Discussion tabs (with Surface Charts + GRAMET PDF/PNG), Offline `/bundle` & 50 MB Chart Cache in `filesDir/BriefingCache`, What's New, and Feedback.
- **Phase 2 (Cross-Section, Route Graph & Skew-T)**: `:rzskewt` thermodynamics & transform library, 17+ layer `CrossSectionCanvas` (with `Square`/`Soft`/`Natural` cloud styles and Web-aligned `thermo-convective-bg` + axes), phone-first `LayerBarView` (integrated model pills + `Focus` preset + pinned `Options` sheet + wrapping `FlowRow` of all 7 canonical `LayerFamily` chips), pixel-aligned `RouteGraphCanvas` with single-row L/R metric controls, and interactive `SkewTCanvas` with dual-axis side panel and Compare Models mode.
- **Phase 3 & 4 (Maps, Observed Tab, In-Flight GPS & Push Plumbing)**: Web Mercator `SlippyMapCanvas` (Stadia dark/muted + OSM light tiles with 30 MB OkHttp disk cache), `RouteMapTabScreen`, `PanEuropeanMapScreen` (Forecast + Historical Replay), flight-day `ObservedTabScreen` with `RouteRibbonCanvas` and `RunwayWindDialView`, `FlightTrackingService` (foreground location service wired to `ObservedTabScreen`), and `PushNotificationManager`. The PIREP sheet and offline queue built here were removed in #1024 (owner dropped PIREPs; the server API stays).
- **Not yet bundled / deferred**:
  - **Instrumented emulator tests (`androidTest`)**: Automated tests currently run as fast JVM unit tests (`./gradlew test :app:testDebugUnitTest`). Compose UI instrumentation tests (`src/androidTest/`) are not yet configured in CI.

## What's Built

### Authentication (`ui/auth/LoginScreen.kt`, `:flyfun-common`)
- Driven by `FlyFunAuthService` (`aero.flyfun.common`):
  - **Sign in with Google**: Chrome Custom Tabs OAuth (`/auth/login/google?platform=ios&state=<nonce>`) → `flyfunweather://auth/callback?code=...&state=...` → `POST /auth/exchange`. *(Note: `AuthConfig.platform` intentionally defaults to `"ios"` because upstream `flyfun-common` on the server branches on `platform == "ios"` to emit custom-scheme `flyfunweather://auth/callback` redirects instead of setting a web cookie.)*
  - **Sign in with Email**: magic-link request (`POST /auth/magic-link`) + code verification sheet.
  - **Dev Login**: `GET /auth/dev-token` in debug builds on the Android Emulator (`BuildConfig.DEBUG && ApiClient.isRunningOnEmulator()`), connected to `https://localhost.ro-z.me:8443` (real devices connect to `https://weather.flyfun.aero`).
  - **Demo Mode (`Try Demo Mode`)**: switches `AppStateViewModel` to `FixtureBriefingRepository` + `FixtureTripRepository` so the full app can be explored offline without a server.
- Session JWT is encrypted at rest via `AndroidTokenStore` (`data/AndroidTokenStore.kt`, using Android Keystore `AES/GCM/NoPadding` 256-bit key in `filesDir/flyfun_auth_token.enc`, with automatic migration from legacy plaintext tokens) and rotated automatically via host-scoped `RollingBearerInterceptor` whenever the configured API server returns `X-Renewed-Token`.
- Reviewer deep-link carve-out (`JwtClaims.shouldAcceptDeepLinkToken`) accepts a bare token in a deep link only when signed out and the token payload carries `"scope": "review"`.

### Flight List & Trips (`ui/flights/`, `ui/trips/`)
- **Adaptive two-pane layout** (`MainActivity.kt`, `FlightListScreen.kt`): on wide tablets/foldables (`maxWidth >= 840.dp`), renders a persistent 360dp flight list pane alongside the detail `BriefingContainerScreen`; on phones (`< 840.dp`), uses single-pane stack navigation with `rememberSaveable` state preservation across rotation and root `BackHandler` support.
- **Flights vs. Trips toggle**: switches between duration-aware collapsible sections (`Future`, `Recent`, `Past`) and multi-leg `Trips` (`TripDetailScreen.kt`: conjunctive chain status, binding leg callout, Haiku trip summary, per-leg cards, and serial trip refresh).
- **Multi-select bulk delete**: long-pressing a flight row or choosing `Select & Delete Flights` from the top bar enters contextual multi-select mode (`POST /api/flights/bulk-delete`).
- **Top bar actions**: quick `Explore Maps` button (opens `PanEuropeanMapScreen`), `+` Add Flight FAB, and `More` menu grouped like iOS (#996): `Open website`, `Settings` | `What's New` (unseen badge dot), `Help` (website `help.html`), `Send feedback` | `Sort`. Aircraft and sign out live in Settings only.

### Add / Edit Flight & Aircraft (`ui/flights/AddFlightSheet.kt`, `ui/aircraft/`)
- Offline ICAO route autocomplete backed by `AirportDatabaseService` (`GET /api/nav/airports-db` with ETag caching) and `:rzflight`'s `KnownAirports.rankedSearch`.
- Native Material 3 date (`DatePickerDialog`, UTC) and 24-hour time (`TimePicker`/`TimeInput` with `:00/:15/:30/:45` chips applied on OK) pickers, an hours + quarter-hour `FlightDuration` picker with a synced slider, cruise altitude & ceiling inputs with live aircraft service-ceiling warning (`AddFlightViewModel.ceilingWarning`, #777), Autorouter route import, and the edit flow (#885) below.
- **Edit / Duplicate** (`AddFlightViewModel.Mode` CREATE / EDIT / DUPLICATE). Pure rules live in `model/FlightEditRules.kt` (unit-tested, mirrors iOS): an edit that changes the departure **UTC day** or the first/last waypoint is structural (the flight id derives from them) and opens `StructuralChoiceSheet` (**Move**: `POST /api/flights/{id}/move`, `keep_in_trip` on by default, pack-count and live-flight warning, then a residual `PATCH` for what `/move` can't carry: aircraft, profile, flexibility, alternate; **Keep both**: create a copy, no trip unless ticked). Anything else is a `PATCH` of only the changed fields, and the response's `invalidation` is acted on (`refetch_needed` queues a refresh, retried in the background on 409; `advisories_only` recalculates the latest pack). A follow-up that fails after the main save commits (residual PATCH, alternate PATCH, refresh queue, recalculation) sets `saveWarning`, shown as a toast once the sheet closes. The impact line above the save button says which will happen. An untouched route keeps its stored waypoints and `raw_route` (prefilled into the route field). Duplicate is reachable from the flight-list menu and the briefing screen's overflow menu, prefilled with the date moved to the next day.
- **Wire contract**: `tests/test_android_api_contract.py` (pytest, runs in CI) parses `ApiClient.kt` and the request DTOs against the FastAPI app, because the server ignores unknown keys and a wrong verb or field name fails silently. Its `KNOWN_BROKEN_*` lists may only shrink; since #893 `KNOWN_BROKEN_CALLS` is empty. The check covers requests and `FlightResponse` only; other response DTOs are not checked (e.g. `PreferencesResponse` read `has_autorouter` for the server's `has_autorouter_creds`). Wire facts that are easy to get wrong: Autorouter linking is flyfun-common at the root (`/autorouter/link-ticket {scheme}` → `{url}`, callback `flyfunweather://autorouter/callback?status=…&code=…`, `/autorouter/link-complete {code}`, `/autorouter/unlink`), route import lists recent routes (`/api/flights/autorouter-routes`) and fills the form via parse-fpl; sharing resolves by code (`/by-share/{code}`) then subscribes by id; all feedback is one `POST /api/feedback` (`FeedbackRequest` factories); a trip's AI paragraph comes with the trip and `POST /ai-summary` is only for a stale one.
- Full aircraft registry CRUD (`AircraftListScreen.kt`, `AircraftFormSheet.kt`) with Make Default and 409 last-aircraft deletion guard.

### Briefing Viewer (`ui/briefing/BriefingContainerScreen.kt`)
- **Top bar (#996)**: leading pack menu; trailing a Start/Stop tracking button (only for an editable flight inside its tracking window, same `rememberFlightTrackingToggle` as the Observed tab's bar) and one ⋮ menu (`briefingMoreMenu`): Edit, Duplicate (disabled offline with "Editing needs a connection", like iOS) | Share link… (`ApiClient.DEFAULT_BASE_URL`/s/…) (owner, non-private) | Send feedback on this briefing. No subtitle: the Advisory tab opens with `FlightSummaryStrip` (`model/FlightSummary.kt`, mirrors iOS `FlightSummary`): ends and plan times, date, duration, level, aircraft, and the route on a tappable line. Android shows plan times only (it doesn't decode the live progress block).
- **Leading Pack Toolbar (`BriefingPackToolbar.kt`)**: displays freshness dot, `D-N` label, assessment badge, and offline cache icon; dropdown switches historical packs, triggers `Download for Offline` (`/bundle`), or starts an SSE streaming `Refresh Briefing` (`POST /packs/refresh/stream`). Opening a flight with no pack (the normal state after `POST /api/flights`) starts the first briefing, unless `/packs/refresh/status` shows a run already in flight (web, another device): then `pollActiveRefresh` follows it (3 s, 100-poll cap, like iOS `checkActiveRefresh`) with the same banner, and reports an error if it ends with no pack. A pack already on screen gets the same background follow and is only reloaded if the run produced a newer one. If the SSE stream drops before `complete` (screen off, app backgrounded), `refreshBriefingInternal` asks `/refresh/status`: an active or unknown (failed check) run is followed by polling; otherwise a newer `latestPack` or a `briefing_ready` provisional pack is adopted. `ApiClient.refreshPackStream` maps only non-2xx responses to `ApiError.ServerError`; a mid-stream drop on a 200 is a `NetworkError`. `BriefingContainerScreen` keeps the screen on while refreshing and calls `onForegroundResume` on `ON_RESUME` (not the initial one), which re-attaches to an active run or adopts a newer pack, with up to 3 retries when the screen needs recovery; a user refresh cancels that job. All 9 pack sub-endpoints load concurrently via `coroutineScope { async { ... } }` in `BriefingViewModel`.

### Pan-European Forecast & Past Maps (`ui/map/PanEuropeanMapScreen.kt`)
- Accessible from the Flight List top bar (`Explore Maps`) or `/maps.html` deep links.
- **Chrome (#996, same layout as iOS `MapChrome`)**: a `Forecast | Past` switch in the top bar plus a hide toggle (Fullscreen icon, `rememberSaveable`) that clears every overlay but the top bar; a solid `TimeBar` (‹ day/hour menu ›, Past adds the date button) under it; a solid `BottomPanel` with the legend and captioned pickers (`Showing` metric, `Models` / `Source`, `Runs` for model sources only). Solid surfaces so controls read over any tiles.
- Ports of iOS `ForecastMapView` / `HistoricalMapView` on one shared marker layer (`AirportMarkerMap`): every watchlist airport (~619) always drawn, no clustering, a filled circle coloured by the active metric, ringed by the per-metric model agreement in a consensus mode (amber when selected), radius stepping with zoom like iOS `AirportMarkerSizing`. Colours, labels and legends come only from the served catalog (`HelpCatalogStore.mapCatalog`, bundled `map-metrics-catalog.json` as baseline) through `ui/map/AirportMapCatalog.kt`, a port of iOS `ForecastMapCatalog` (categorical, `threshold_asc`/`threshold_desc` with `m_to_sm`, `null_color`, numeric `fallback`, `gray_ramp`, `alternate_needed` aggregated per mode); the metric menu is the pilot-question list.
- **Forecast** (`ForecastMapViewModel`): day menu from `/api/maps/forecast/days` (unavailable days listed, disabled), hour stepper, model mode Worst / Majority / GFS / ICON / ECMWF (a model that can't reach the day explains itself), metric and model switches are a pure recolour, only a day/hour change fetches; an 8-slot LRU plus adjacent-hour prefetch (one request per slot: stepping onto a prefetch in flight awaits it); a failed day/hour fetch clears the map and shows the error with Retry, never the previous slot under the new label; cold open on the nearest sample hour to now and centred on the pilot's usual departure (`/api/flights/frequent-airports`). The airport card is a metric × model matrix with the consensus column, alternate-required row and init times; a row tap recolours the map.
- **Historical** (`HistoricalMapViewModel`, #629): an instant on the server's 30-min grid (`/api/maps/historical/range`; date picker, ‹ time ›, lead Latest / D-1…D-6), source METAR / TAF / Worst / Majority / GFS / ICON / ECMWF presented to the marker layer as the one "model" read (`HistoricalMapAirport.forecastAirport`); all selection is server-side (`/api/maps/historical?at=&lead=`). A status line says what the map shows or why a source is empty; the card compares METAR, TAF and the three models with provenance and the raw reports.
- Neither map has stand-in data: a failed load shows the error with Retry, and demo / guest mode says the maps need an account (iOS fixture mode throws the same way). Before this port both maps read an invented payload shape, failed on every call and silently drew a 15-airport fixture.
- Deep links (`UniversalLinkRouter`): `fc.day` / `fc.date` / `fc.hour` / `fc.model` / `fc.metric` / `fc.apt`, and `hist.date` + `hist.time` / `hist.lead` / `hist.source` / `hist.metric` / `hist.apt`; each tab's `*.view` (`lat,lon,zoom`, Leaflet zoom + display density) positions the camera. Not ported from iOS: the locate-me button.

### In-Flight GPS Service & Push (`service/`)
- **`FlightTrackingService.kt`**: Android `foregroundServiceType="location"` service (`START_STICKY`) with compact ongoing notification, invoked from `ObservedTabScreen` after runtime location permission grant (`ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`). Projects GPS fixes onto the active route via `LivePositionRules.projectOntoRoute` and posts sparse updates (`POST /api/flights/{id}/live/position` when $\Delta t \ge 3\text{ min}$, $\Delta d \ge 8\text{ NM}$, or $\Delta alt \ge 800\text{ ft}$), at most 5 fixes a post (the server's limit). The fix JSON is the server's `LivePositionFix` (`at`, `alt_ft`, `gs_kt`, `track_deg`, required `h_accuracy_m`; a missing value is omitted, never 0, which the server would read as on the ground); before #874 it used other field names and a nonexistent `/api/live-position` fallback, so no Android fix ever reached the server. Landing auto-stop (#874, iOS rule): a valid ground speed < 30 kt within 5 NM of the destination, only after a fix at ≥ 30 kt was seen (so a round trip or a short hop is not "landed" on the ground at Start), posts `landed: true` and stops the service once that post goes through; one that fails for want of data is retried with each next fix, tracking running on meanwhile. **Queue on disk (#889):** after every fix the unsent queue and pending landing are saved per flight in `PendingFixStore` (`<filesDir>/pending_position_fixes.json`, written via tmp + move), together with the session (flight id, waypoints, end time). A `START_STICKY` restart after a process kill (null intent) restores the session, so fixes keep being queued even before the app has an API client. On app start (`AppStateViewModel.refreshUserSupportData`) `uploadPersistedFixes` posts every stored queue except the running session's, and hands a restored session its client. Restarting tracking for the same flight picks its stored fixes back up but drops a stored landing (Start again means not landed). Sign-out discards the file. Bounded: one queue per flight, each trimmed to `MAX_BUFFERED_FIXES`. Unlike iOS, Android persists no started/landed state: "started" means "being tracked now", so after a kill a late leg's windows fall back to the planned ones (the server still infers the landing from a later ground fix). `BriefingContainerScreen` re-runs the tab reconcile when tracking starts or stops. Queued fixes go oldest first in batches of 5, removed only once sent. Without a known departure (flight not loaded) the auto-stop falls back to 12 h after Start. It also stops itself at `FlightResponse.trackingWindowEndEpochMs(started = true)`, the latest take-off the server accepts (`MAX_TAKEOFF_DELAY_HOURS`, 6 h) + duration + 2 h. Start is not window-gated on Android. Automatically stopped on `AppStateViewModel.logout()`.
- **`PushNotificationManager.kt` + `FlyFunMessagingService.kt` (FCM)**: Firebase project `flyfun-weather-494e0`; its `app/google-services.json` is untracked (like the upload key) and the `google-services` plugin applies only when it is present, so CI and other checkouts build with push off (`FirebaseApp` absent → token calls no-op) and `bundleRelease`/`assembleRelease` fail without it. Channels are created in `FlyFunWeatherApp.onCreate`. Every signed-in start (`refreshUserSupportData`) fetches the FCM token and `POST /api/devices` with `platform = "android"` (the server upserts); `onNewToken` re-registers while signed in. Sign-out deletes the FCM token (the request could no longer be authenticated), so the server's next send gets `UNREGISTERED` and drops the row. Android 13+ `POST_NOTIFICATIONS` is asked once per install on the first signed-in start. Delivery: a message with a `notification` block is shown by the system in the background (tap → `MainActivity` with the data keys as string extras → `handleNotificationIntent` → `AppStateViewModel.navigateTo`); in the foreground `onMessageReceived` posts it via `showLocalNotification`. `parsePayload` reads the server's `flight_id` / `type` (`live_alert`, `live_clear`, `flight_day`) / `interruption_level` and mirrors `_fcm_channel_id_for_payload`; live types open the Observed tab. Trip pushes (no `flight_id`) only open the app.
